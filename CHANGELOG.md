### Added
- **Audit report `QURAN-DHIKR-AUDIT-2026-10-20.md`** — a detailed, line-referenced engineering audit of the **second and third menu sections** (`sec-quran`: `mushaf.html`, `mushaf-quran.html`, `Quran-radio.HTML`, `takbeer.html`; `sec-dhikr`: `adhkar.html`, `nawawi.html`, `du'a.html`, `dua-guide.html`, `ruqyah.html`, `sunan.html`, `asma.html` — 11 pages, 626 KB), plus the shared logic they actually run through (`js/app.js` `initMushaf`/`initTasbih`/`applyQuranFont`, `js/core/state-manager.js`, `profile.js`). **2 critical / 6 high / 6 medium / 8 notes**, each with file:line evidence. Every numeric claim was proven by *executing the real extracted code* in a sandbox rather than by review, and the report carries an explicit **«what was withdrawn after verification»** appendix listing five initial findings that turned out to be false — including `getVolume()`'s `|| 80` (correct, because `input[type=range].value` is the *string* `'0'`, which is truthy), `window.STATE` being "never defined" (it is assigned at `state-manager.js:119/153/177/188`), `asma.html`'s `toggleFav` toast (correct, because `includes()` is evaluated *after* the mutation), and the radio page's `toggleTheme` "losing OLED" (the function is dead code — `app.js`'s 3-way cycler wins). The suggestions half is researched against the 2026 Quran- and dhikr-app market with **35 cited sources**, each mapped to the specific claim it supports. No fix from this report has been implemented yet.
- **`js/vendor/geomag.min.js` — a locally vendored World Magnetic Model (WMM-2025) engine** (11 KB, `window.ZadMag`, Apache-2.0 via `geomagnetism@0.2.0`, licence kept at `js/vendor/LICENSE-geomagnetism.txt`). `ZadMag.field(lat, lng, date?)` returns `{decl, incl, valid, reason, model}` and **never throws**: bad coordinates, an invalid date or an out-of-validity date come back as `valid:false` with a machine-readable `reason` (`bad-coords` / `bad-date` / `out-of-range` / `non-finite`) instead of an exception, and `ZadMag.validity` exposes the model window (2024-11-13 → 2029-11-13). Added to the service-worker `PRECACHE` alongside `qibla.html` — without it the page would open from cache offline and the correction would die exactly when it is needed. Verified against a Node reference run of the same model: **maximum difference 0.000000000° across 9 cities** (Cairo +4.772°, Makkah +3.502°, Alexandria +4.851°, London +1.214°, New York −12.462°, Sydney +12.827°, Rio −23.014°, Tokyo −7.943°, 89°N +13.292°).
- **A magnetic-declination readout in `qibla.html`** — a new `#qi-decl` row (🧲 «الانحراف المغناطيسي») in the info panel showing the local value (`+4.8°` in Cairo) with a tooltip explaining that it is applied automatically. It renders `—` when the model is unavailable, so the UI always tells the truth about whether the correction is live.
- **`updateDeclination(lat, lng)`** in `qibla.html`, called from `applyQibla()` — the single place where coordinates become available — so the correction refreshes for every location source (GPS, preset city, manual entry, map pick, search) rather than only on first load. Sets `Q_declination` / `Q_declValid` and degrades to a **zero correction, never a broken compass**, if `ZadMag` is missing or blocked.
- **`compassHeadingRaw()` / `magneticHeading()` / `screenAngle()`** in `qibla.html` — a tilt-compensated heading from the full rotation matrix, with `compassHeadingRaw()` returning `null` (not `0`) at its mathematical degeneracy, and `magneticHeading(e)` falling back to the legacy `norm(360 - alpha)` in that case only. `screenAngle()` reads `screen.orientation.angle` so landscape use is compensated.
- **Prayer-time notifications (`js/prayer-notifications.js` + `.min.js`)** — closes P1-7, the largest gap in the section: the app had zero adhan alerts. New `window.ZadPrayerNotif` module computes today's and tomorrow's times **on-device** through the vendored adhan engine (so it works offline), schedules on the absolute instant rather than a written clock time (immune to device timezone and DST), and re-arms on `visibilitychange` / `focus` / `online`, after each fired notification, and at midnight. A `zad_prayer_notif_last` ledger prevents duplicates when re-scheduling. Settings live under `zad_prayer_notif`: master switch, per-prayer toggles, an "adhan minus N minutes" lead (0/5/10/15/20), and a separate Jumu'ah reminder 45 minutes before Dhuhr. Added to the service-worker `PRECACHE`.
- **Notification UI** — a «تنبيه الأذان» card in `settings.html` (master switch, five per-prayer rows showing today's computed time, Jumu'ah toggle, lead-time selector, a "🔔 جرّب إشعارًا" test button, and a battery-troubleshooting panel) plus a «🕌 نبّهني عند الأذان» button in the `prayers.html` hero that reflects live state and hides itself if the module failed to load.

This addresses the single most common store complaint about prayer PWAs: notifications silently killed by the OEM battery manager.

### Changed
- **`sw.js`: `CACHE_STATIC` bumped `…-prayer-audit-r2` → `…-prayer-audit-r3`** and `./js/vendor/geomag.min.js` added to `PRECACHE`, so returning PWAs pick up the corrected qibla page and its declination model together. All 82 precache entries were verified to exist on disk — a missing one fails the whole install, not just that asset.
- **The hero countdown is now driven by the live Hijri date** instead of fixed 1447 anchors. `startCountdown()` reads `window.getHijriDate()` and resolves its anchors through `findHijriDateInGreg()`, so it renews every Hijri year and respects the user's offset. Eid greetings are now confined to 10–13 Dhul Hijjah (Eid plus the days of Tashreeq) rather than "anything past day 9". See P0-7.
- **The Arafah reminder date is computed, not hardcoded**, in both `js/app.js` (`scheduleReminders`) and `settings.html` (`scheduleAllReminders`) — it was `new Date(2026, 4, 26)`, i.e. dead since 26 May 2026. The `settings.html` row label that read «26 مايو 2026» now shows the computed date.
- **All existing reminders now deliver through the Service Worker.** `settings.html` `scheduleAllReminders()` and `js/app.js` `scheduleReminders()` previously called `new Notification(...)` directly, which never renders on Chrome/Android — so the morning/evening wird, morning/evening adhkar, Arafah and Friday-video reminders were scheduled successfully and shown to nobody. They also now carry a `data.url` so tapping one opens the relevant page (`arafah.html`, `videos.html`, `index.html`). See P0-8.
- **The "quiet hours" policy moved from scheduling time to delivery time.** `js/design-system.js` used to block `scheduleReminders()` entirely between 00:00 and 05:00 with no retry, so anyone who enabled notifications overnight received nothing at all — including Fajr. `zadNotify()` now defers *non-prayer* notifications to 05:00 and exempts prayer ones (tags `zad-prayer*` / `zad-jumuah`), and scheduling is never blocked. See P1-9.
- Rebuilt `js/app.min.js`, `js/design-system.min.js` and `js/calendar.min.js` with `terser --comments false` only. Before editing, each committed `.min` was rebuilt from its committed source and matched byte-for-byte (modulo a trailing newline), which proves the diff contains only the intended changes.
- **`calcPrayerTimes()` rewritten for the adhan 4.x API** — it now passes a plain `Date` to `PrayerTimes` instead of the removed `DateComponents`, resolves the app's method keys through a new `ADHAN_KEY` map (`Egypt`→`Egyptian`, `MWL`→`MuslimWorldLeague`, `ISNA`→`NorthAmerica`), and accepts an `opts` argument (`method`, `madhab`, `timezone`). See P0-6 in the audit report.
- **Prayer times for a chosen city are now rendered in that city's timezone**, not the device's. `adhan.PrayerTimes` returns absolute instants, so picking Makkah while sitting in Cairo used to show Maghrib as 14:52 instead of 17:52.
- **The two engines now share one calculation method.** `getPrayerMethod()` prefers the numeric `zad_prayer_method_id` written by `prayers.html` and translates it via `ALADHAN_TO_ADHAN`; `setPrayerMethod()` writes both keys back through `ADHAN_TO_ALADHAN`. An unknown or corrupt stored key falls back to Egypt instead of silently to Umm al-Qura. (P1-5)
- Rebuilt `js/calendar.min.js` with `terser --comments false` only — **no `--compress`, no `--mangle`** — matching the convention documented in the `sw.js` Z20 comment, because the modal's generated `onclick=` handlers call these function names by string. Internal identifiers are preserved (`offset`, `adjusted`, `date`, `fmt`, `parts`).
- **`prayers.html` calculation-method labels corrected against the official aladhan table** (P0-1): the values were cyclically shifted, so choosing "MWL" actually requested method 3 with 15° Fajr — roughly 20–25 minutes early in Egypt. Labels now read from the authoritative ids, and the mislabelled `value=1` option was removed.
- **Default calculation method unified on Egypt** (Egyptian General Authority of Survey, id 5) in both engines: `js/calendar.js` now defaults to `'Egypt'` and `CALC_METHODS` is reordered Egypt-first, matching `prayers.html`. Previously the two engines disagreed.

- **P2-Q13 — زرّ العدّ يصير ميتًا لو غابت طبقة الحالة.** `getCount()` في `adhkar.html` كانت محروسة بالكامل (`window.STATE?.adhkar`) بينما `setCount()` تستخدم `STATE` عارية وتُنادى في أول سطر من `tap()` قبل أي تحديث للواجهة — فترمي وتترك الزرّ بلا رقم ولا شريط. الكتابة الآن لا ترمي أبدًا وتعيد `false`، ومسار `_openSec` محروس بالمثل.
- **P2-Q14 — كتّاب `zad_v2` المتنافسون.** `mushaf-quran.html` كان يكتب `zad_v2` مباشرة بعد `JSON.parse` (كتابة غير مرئية لـ`STATE` المقيم في الذاكرة، فأي `saveState()` لاحق يمحوها)، وIIFE تتبّع الورد في `mushaf.html` كانت تفعل الشيء نفسه بمفتاحها الخاص. كلاهما يمرّ الآن بطبقة الحالة (`applyQuranFont` / `STATE` + `saveState`) مع مسار احتياطي عند غيابها. باقٍ كتلة `toggleTheme` الميتة في `Quran-radio.HTML` (P3-Q16) ولا أثر حيًّا لها.
- **A self-sustaining re-render loop in the clock-format code, on every page** (roadmap item «ب», single-state/observer work). `applyClockFormat()` assigned `el.textContent` unconditionally, and assigning `textContent` always produces a `childList` mutation — even when the string is unchanged. `initClockFormat()` observes `childList` on `.main` with `subtree: true`, so every pass re-triggered the observer, which scheduled another pass 200 ms later: an endless ~5 Hz re-render of every clock element, app-wide. Writes now go through `_setTimeText()`, which skips identical values, so the loop terminates while the observer keeps doing its real job (picking up clocks rendered dynamically). Proven by `test-clockfmt.js`, which extracts the real functions and counts `textContent` writes: **4 writes on the second pass and 40 across ten passes before; 0 after** — and a genuine format change (24h → 12h) still updates to `5:05 م` and then settles.

- **P1-10: `360 - alpha` ignored the phone's tilt, producing errors up to 90°.** Correct only when the device is perfectly flat or upright with no roll; with any lateral tilt `alpha` is a rotation about the *device's* Z axis, not about north. The two formulas were compared numerically before either was trusted: they agree to **0.000°** for flat (`beta=gamma=0`) and upright (`beta=90, gamma=0`) — the two most common postures — but diverge by 17.2° at `beta=60/gamma=15`, **49.1°** at `beta=60/gamma=45` and **90.0°** at `beta=60/gamma=90`. Replaced with the rotation-matrix formula, shipped as a **hybrid**: the well-known tilt-compensated formula *degenerates* at exactly `beta=gamma=0` (`Vx=Vy=0` ⇒ `atan(0/0)`), where a naive `return 0` guard would output 0° for any `alpha` — so `compassHeadingRaw()` returns `null` at the degeneracy (`|Vx| < 1e-9 && |Vy| < 1e-9`) and `magneticHeading(e)` falls back to the exact `norm(360 - alpha)` there. Flat and upright behaviour is unchanged to 0.0000°; tilted use is now corrected. Swept across `beta` −90…90 × `gamma` −90…90, every posture yields a finite bearing in `[0,360)`.
